## Product design

### Goals / Non-goals

**Goals (v1):**

- An Agent, given credentials for one Azure AD (Entra ID) app registration, can:
  1. List the Azure subscriptions that app registration can see.
  2. Get details of one subscription.
  3. List resources inside a subscription (optionally filtered by resource group / resource
     type).
  4. List Azure Advisor recommendations for a subscription (optionally filtered by category:
     Cost / Security / HighAvailability / Performance / OperationalExcellence).
  5. List Azure Resource Health / Service Health events for a subscription (service issues,
     planned maintenance, health/security advisories).
  6. List the Azure Monitor metric names available for a specific resource (discovery step,
     so metric names aren't guessed).
  7. Get Azure Monitor metric time-series values for a specific resource.
- All read-only, all per-request credentialed (no server-side stored tenant credentials), so
  the server stays stateless and multi-tenant-safe by construction.

**Non-goals (v1):**

- No write/mutate tools (no resource creation/deletion, no "apply this Advisor
  recommendation", no "acknowledge this health event"). Nothing in the ticket asks for
  mutation, and Advisor/Resource Health/Monitor/Subscriptions are inherently
  read/reporting surfaces.
- No Azure Government / China 21Vianet / Germany sovereign-cloud support. Only public cloud
  (`management.azure.com`). Not blocking — same pattern `ms-graph-mcp` uses for its own
  `GRAPH_BASE_URL` override, can be added the same way later if asked.
  **Open question (non-blocking):** none raised by the reporter; flagged here only so a
  future sovereign-cloud ask isn't mistaken for scope creep.
- No Azure Monitor **Activity Log** (subscription-wide "who changed what" audit trail) in v1.
  The ticket's wording ("resource health, and subscription data") maps to Resource
  Health/Subscriptions, not Activity Log; Activity Log is a distinct ARM endpoint
  (`Microsoft.Insights/eventtypes/management/values`) that could be added as a follow-up tool
  if a future ticket names it. Not blocking.
- No Log Analytics / KQL query execution — different API surface, not requested.

### Acceptance criteria AC1..ACn

- **AC1**: Given valid `X-Azure-Tenant-Id` / `X-Azure-Client-Id` / `X-Azure-Client-Secret`
  headers for an app registration with Reader access on at least one subscription, When
  `azure_list_subscriptions` is called, Then the response lists each visible subscription's
  id, display name, and state.
- **AC2**: Given a valid `subscription_id`, When `azure_get_subscription` is called, Then the
  response returns that subscription's id, display name, state, and tenant id. Given an
  unknown or inaccessible `subscription_id`, Then the response is a structured `not_found`
  error naming the subscription id.
- **AC3**: Given a valid `subscription_id` and no filters, When `azure_list_resources` is
  called, Then resources in that subscription are returned (default page size 50, `has_more`
  set when truncated). Given `resource_group` and/or `resource_type` filters, Then only
  matching resources are returned.
- **AC4**: Given a valid `subscription_id`, When `azure_list_advisor_recommendations` is
  called, Then Advisor recommendations for that subscription are returned. Given a `category`
  filter (one of Cost/Security/HighAvailability/Performance/OperationalExcellence), Then only
  recommendations in that category are returned.
- **AC5**: Given a valid `subscription_id`, When `azure_list_resource_health_events` is
  called, Then current/recent Service Health events (service issues, planned maintenance,
  health/security advisories) for that subscription are returned.
- **AC6**: Given a valid ARM `resource_id`, When `azure_list_resource_metric_definitions` is
  called, Then the available metric names and units for that resource are returned.
- **AC7**: Given a valid ARM `resource_id`, a metric name taken from AC6's output, and a
  timespan, When `azure_get_resource_metrics` is called, Then the time-series values for that
  metric over that timespan are returned. Given an invalid/unknown metric name, Then the
  response is a structured `invalid_argument` error naming the bad metric.
- **AC8**: Given any tool call missing one or more of the three required headers, Then the
  server returns HTTP 401 listing the missing header name(s) without calling Azure.
- **AC9**: Given credentials Azure AD rejects (bad client secret, unknown tenant) or that lack
  the RBAC Reader role on the target subscription, Then the tool returns a structured
  `unauthorized` error rather than a 500 or an unhandled exception.
- **AC10**: Given Azure returns `429` on any upstream call, Then the tool retries with
  backoff respecting `Retry-After` up to the single-call time budget (<120s), and if still
  failing returns a structured `rate_limited` error.
- **AC11** (multi-tenant / per-request isolation): Given two concurrent tool calls that carry
  different Tenant Id / Client Id / Client Secret headers, Then each call's Azure AD token
  exchange and response data are scoped to that call only — no credential or token leaks
  across requests. This is the connector's multi-tenant-safety equivalent (there is no
  frontend here, so the "hit the backend" quality-bar requirement in `testcase.md` is met by
  testing this contextvar-isolation behavior directly).

Not blocking implementation — all Open questions above are already resolved with explicit,
documented assumptions; none require a product answer before dev can start.

## Tech design

### Conclusion

Build the first version of `MSPbotsAIFramework/azure-mcp` as a standard header-credentialed,
stateless vendor MCP server (Python 3.12 + FastMCP, per SOP §9), with 7 read-only tools
covering Azure Subscriptions, Resource inventory, Advisor, Resource Health, and Monitor
metrics. Auth is direct Azure AD (Entra ID) OAuth2 client-credentials, not a
gateway-passed-token like `ms-graph-mcp` — see "Decisions made by DEV01" for why that pattern
was not reused here.

### Where the current implementation lives

Nowhere yet. `azure-mcp@main` (6791c0c) is an empty scaffold (`README.md` only). This is a
from-scratch build; "where it lives" below describes where the dev leg should put each piece,
following the structure the SOP (`vendor-mcp-development-sop.md` §9) and sibling repos
(`ms-graph-mcp`, `halopsa-mcp`) already use:

- `server.py` / `app.py` — FastMCP app, `/mcp` (Streamable HTTP, `stateless_http=True`) +
  `/health` (local-only probe).
- `azure_mcp/auth.py` (or `middleware.py`) — reads the three headers, does the client-credentials
  token exchange, sets a `contextvars.ContextVar`, resets in `finally`.
- `azure_mcp/client.py` — thin ARM HTTP client: base URL `https://management.azure.com`,
  shared `httpx` client per request, timeouts, retry/backoff on 429/5xx.
- `azure_mcp/tools/` — one module per capability area (`subscriptions.py`, `resources.py`,
  `advisor.py`, `resource_health.py`, `monitor.py`), each registering its tool(s).
- `azure_mcp/errors.py` — the structured error envelope + the Azure-HTTP-status → `code`
  mapping (see Data & API contract).
- `tests/test_tools.py`, `tests/test_middleware.py` — per SOP §10 minimum set.
- `Dockerfile`, `pyproject.toml`/`uv.lock` — per SOP §8.

### Option analysis

**Auth pattern: direct client-credentials vs. gateway token passthrough**

- **Chosen: direct client-credentials.** The server itself exchanges
  `X-Azure-Tenant-Id` / `X-Azure-Client-Id` / `X-Azure-Client-Secret` for an ARM access token
  per request (`scope=https://management.azure.com/.default`), the way most other MSPbots
  connectors work (SOP §3.1 default pattern; also matches the wiki's "OAuth app" connect-form
  variant seen on ConnectSecure/Acronis/BizRatings — Client ID + Client Secret (+ Tenant), not a
  caller-supplied bearer token).
- **Rejected: `ms-graph-mcp`-style gateway passthrough** (`X-Ms-Graph-Token`, caller already
  holds a valid access token and the server just forwards it). That pattern exists there
  because MSPbots already has an established OAuth/consent flow for the Microsoft **Graph**
  scope, wired through the platform's own token broker. There is no equivalent existing broker
  for the ARM (`management.azure.com`) scope — a customer's Azure subscriptions need their own
  app registration and an RBAC role assignment on each target subscription, independent of
  any Graph consent. Building a new broker integration to reuse that pattern here would be far
  more work than the standard header-credentialed model this SOP already supports, for no
  functional gain in v1.

**Tool granularity: curated capability tools vs. a generic ARM passthrough tool**

- **Chosen: 7 named, purpose-built tools** (see Change list). Matches SOP A4: "tools are
  capabilities, not API-endpoint mirrors."
- **Rejected: one generic `azure_arm_get(path, api_version, query)` tool.** Would technically
  cover every ARM GET in one tool, but reintroduces the thing SOP A4 explicitly forbids
  (endpoint mirroring), loses structured per-capability error mapping and token-economy
  controls (list/paginate defaults), and pushes ARM API knowledge (exact paths, api-versions)
  onto the calling Agent instead of the server. Rejected.

### Data & API contract

**Credential headers** (all required; missing any one → AC8's 401):

| Header | Type | Required | Meaning |
|---|---|---|---|
| `X-Azure-Tenant-Id` | string | yes | Azure AD tenant (directory) id the app registration lives in |
| `X-Azure-Client-Id` | string | yes | App registration (service principal) client id |
| `X-Azure-Client-Secret` | password (masked) | yes | App registration client secret |

**Token exchange** (per request, never cached across requests — see Non-functional):

```
POST https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id={client_id}&client_secret={client_secret}
&scope=https%3A%2F%2Fmanagement.azure.com%2F.default
```
→ `access_token` used as `Authorization: Bearer <token>` on every `management.azure.com` call
below. A failure here (invalid tenant/client/secret, `AADSTS...` error body) maps to the
`unauthorized` error code (AC9) — never a 500.

**ARM endpoints used** (API versions are the latest stable at design time; dev leg should
confirm against Microsoft's current docs before wiring, since Microsoft revs these
periodically):

| Tool | Method + path | Notes |
|---|---|---|
| `azure_list_subscriptions` | `GET /subscriptions?api-version=2022-12-01` | no `subscription_id` param |
| `azure_get_subscription` | `GET /subscriptions/{subscription_id}?api-version=2022-12-01` | 404 → `not_found` |
| `azure_list_resources` | `GET /subscriptions/{subscription_id}/resources?api-version=2021-04-01&$filter=...&$top=...` | `$filter` built from optional `resource_group`/`resource_type` args |
| `azure_list_advisor_recommendations` | `GET /subscriptions/{subscription_id}/providers/Microsoft.Advisor/recommendations?api-version=2023-01-01` | optional `$filter=Category eq '<category>'` |
| `azure_list_resource_health_events` | `GET /subscriptions/{subscription_id}/providers/Microsoft.ResourceHealth/events?api-version=2022-10-01` | covers service issues, planned maintenance, health/security advisories |
| `azure_list_resource_metric_definitions` | `GET /{resource_id}/providers/Microsoft.Insights/metricDefinitions?api-version=2024-02-01` | `resource_id` is a full ARM resource id, e.g. from `azure_list_resources` output |
| `azure_get_resource_metrics` | `GET /{resource_id}/providers/Microsoft.Insights/metrics?api-version=2024-02-01&metricnames=...&timespan=...&interval=...&aggregation=...` | invalid `metricnames` entry → `invalid_argument` naming the bad metric |

**Pagination** (SOP token-economy requirement): `azure_list_*` tools default `limit=50`, hard
cap `limit<=200`, `has_more` set from ARM's `nextLink` presence; the server stores no cursor
state — it requests ARM's `$top`/`$skiptoken` as applicable and surfaces `has_more` only
(no raw `nextLink` passthrough, to keep the contract stable regardless of ARM's own
pagination mechanics across these different resource providers).

**Structured error envelope** (SOP §4, not an exception):

```json
{"error": {"code": "unauthorized", "message": "...", "retryable": false}}
```

| Azure/local condition | `code` | `retryable` |
|---|---|---|
| missing credential header(s) (AC8) | `unauthorized` | false |
| Azure AD token exchange rejected / ARM 401/403 (bad secret, missing RBAC Reader role) (AC9) | `unauthorized` | false |
| subscription/resource not found (404) (AC2) | `not_found` | false |
| bad parameter (bad metric name, malformed filter) (400) (AC7) | `invalid_argument` | false |
| `429` (AC10) | `rate_limited` | true |
| any other 5xx / unexpected upstream failure | `upstream_error` | true |

### Key flow / sequence

```
Agent -> POST /mcp (tool call + 3 Azure headers)
  -> auth.py: all 3 headers present? no -> 401 (AC8)
  -> auth.py: POST login.microsoftonline.com/{tenant}/oauth2/v2.0/token
       -> rejected -> {"error":{"code":"unauthorized",...}} (AC9)
       -> ok -> access_token stored in this request's ContextVar
  -> tools/<module>.py: build ARM request using access_token, call management.azure.com
       -> 404 -> not_found | 400 -> invalid_argument | 403 (RBAC) -> unauthorized
       -> 429 -> bounded retry w/ Retry-After -> still failing -> rate_limited (AC10)
       -> 2xx -> map ARM JSON -> compact tool response (limit/has_more where applicable)
  -> ContextVar reset in `finally` regardless of outcome (AC11)
```

### Non-functional

- **Statelessness / multi-tenant isolation**: credentials and the derived access token live
  only in a per-request `ContextVar`, set at request start and `reset()` in `finally` — never
  a module-level/global cache (SOP §3.3/§3.4). Consequence, stated explicitly as a deliberate
  trade-off: **every tool call does its own full OAuth2 token exchange** (no token caching
  across requests, even for the same tenant), adding one extra HTTP round-trip
  (~100-300ms typical) per call. Accepted because the SOP's isolation rule is explicit that
  derived tokens must not be cached across requests, and this is a connector a customer's
  Azure app-registration secret flows through — correctness beats shaving one round trip.
- **Outbound robustness**: 5s connect / 30s read timeout; limited retry+backoff on 429/5xx
  respecting `Retry-After`; single tool call budget < 120s; one shared `httpx` client per
  request (not a global pool holding credentials).
- **Security**: no credentials or tokens in logs; log `tenant_id` (not secret) +
  `subscription_id` + tool name + outcome for traceability. `X-Azure-Client-Secret` is the
  only `password`-typed header (masked in the connect form and in `credential_fields`
  registration). RBAC: the app registration must be granted at least the **Reader** role on
  each subscription it should see — this is a customer/Azure-side prerequisite documented in
  the README's setup steps, not something this server can or should automate (consistent with
  every other MSPbots connector: the server consumes a grant, it doesn't manage consent).
- **Rate limits**: ARM enforces subscription-level throttling; the bounded retry/backoff above
  is the only mitigation in v1 — no client-side request queueing/smoothing, which would be
  over-engineering for a v1 read-only connector with no confirmed high-volume use case yet.

### Decisions made by DEV01

Per `mcp-track.md` §2.4 (new-MCP judgment calls to be flagged, not silently assumed):

- **Direct client-credentials auth, not `ms-graph-mcp`'s gateway-passthrough pattern.** Why:
  ARM is a distinct scope/app-registration from Graph; there is no existing token broker for
  it to reuse. Alternative (gateway passthrough): rejected, see Option analysis above.
- **7 named capability tools, not a generic ARM passthrough tool.** Why: SOP A4 forbids
  endpoint-mirroring tools; a generic tool would also skip structured error mapping and
  token-economy pagination controls. Alternative: rejected, see Option analysis above.
- **Added `azure_list_resources` and `azure_list_resource_metric_definitions` as supporting
  discovery tools**, even though neither is literally named in the ticket. Why: without
  `azure_list_resources`, nothing in this service can produce the ARM resource id that
  `azure_get_resource_metrics` requires; without `azure_list_resource_metric_definitions`,
  the Agent would have to guess metric names and hit `invalid_argument` repeatedly.
  Alternative (omit both, let the Agent supply ids/metric-names it somehow already knows):
